# Design: กลุ่ม 6 PR-C — `line-webhook` (บอท LINE) กรองตามแผนก

วันที่: 2026-10-26 · ฐาน: `main` @ `7b20def` (รวม #75) · branch: `feat/scope-g6c-line-webhook`
สถานะ: **อนุมัติโดยเจ้าของ 26 ต.ค.; ทำเสร็จใน PR-C (กลุ่ม 6)** · ตรวจโดย builder check แล้ว 1 รอบ; เจ้าของตอบ 2 ข้อ: role `User` ให้ตรงกับเว็บ, Vendor ไม่ให้ดูสต็อกแล็บ

## 1. เจตนาและเหตุผล

`src/app/api/line-webhook/route.ts` คือบอท LINE ที่รับข้อความ/postback จากผู้ใช้ มันเป็นไฟล์สุดท้ายที่ยังตอบข้อมูลสต็อก / ใบสั่งซื้อ (PO) / พัสดุโดยไม่รู้จักแผนก และตอนนี้ **ใครก็ตามที่เพิ่มบอทเป็นเพื่อนก็พิมพ์ `PO-...` หรือเลขพัสดุแล้วเห็นข้อมูลได้ โดยไม่ต้องผูกบัญชี** (`route.ts:214-268`, ตรวจที่ `main` 7b20def)

เป้าหมายของ PR นี้คือเมื่อสวิตช์ `DEPARTMENTS_ENABLED` เปิด บอทต้องตอบเฉพาะข้อมูลที่ผู้ใช้มีสิทธิ์เห็น และตอนสวิตช์ปิด (สถานะ production ตอนนี้) **ต้องตอบเหมือนเดิมทุกอย่าง** นี่คือชิ้นสุดท้ายของกลุ่ม 6 หลัง PR-A (#74) และ PR-B (#75) ทำให้ `DEPARTMENT_SCOPE_PENDING` เหลือ 2 (`auth/register`, `mobile/lookup` ตั้งใจค้าง)

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / สิ่งที่ถือว่าล้มเหลว

**เป้าหมาย**
- สวิตช์เปิด: ข้อความสต็อก (3 รูปแบบ), `PO-...`, เลขพัสดุ ตอบเฉพาะข้อมูลของผู้ใช้ที่ผูกบัญชี LINE แล้ว
- **สต็อก:** เจ้าหน้าที่แล็บทุก role (Admin/Manager/User) เห็นเฉพาะแผนก default ของตัวเอง; **Vendor ดูสต็อกแล็บไม่ได้** (เจ้าของตัดสิน 26 ต.ค.)
- **PO และพัสดุ (เจ้าหน้าที่แล็บ):** เฉพาะผู้ที่ **role ที่มีผลจริงในแผนก** เป็น Admin/Manager (`isLabPurchasingRole`) เหมือนหน้าเว็บ (`purchase-orders/route.ts:18`, `vendor/shipments/route.ts:49-50`); role `User` ได้ข้อความปฏิเสธ (เจ้าของตัดสิน 26 ต.ค. "ให้ตรงกับเว็บ") และกรองแผนก default
- **PO และพัสดุ (Vendor):** เห็น **ของบริษัทตัวเองเท่านั้น (กรองด้วยชื่อ vendor ไม่กรองแผนก)** ตามนโยบาย A ที่ใช้กับ `vendor/shipments` และ PO บนเว็บ
- ถอด `src/app/api/line-webhook/route.ts` ออกจาก `DEPARTMENT_SCOPE_PENDING` (3 → 2)
- สวิตช์ปิด: ข้อความ SQL, จำนวน query, คำตอบ เหมือนเดิมทุกไบต์ (มี baseline เทสต์คุม)

**ไม่ใช่เป้าหมาย**
- ไม่แก้คำถาม Vendor ใช้ร่วมหลายแผนก (ข้อ 3 ใน `docs/departments-rollout.md`) — ยังไม่ตัดสิน
- ไม่เพิ่มคำสั่งใหม่ ไม่เพิ่มตัวเลือกเลือกแผนกใน LINE (ใช้แผนก default เท่านั้น เหมือน LIFF สั่งซื้อ)
- ไม่แก้ `ack_expiry` / SQL ของ postback (`route.ts:305-307`, `:327-335`) / `ensureExpiryAcknowledgementSchema`
- ไม่แก้ `line-liff-auth.ts`, ไม่เปิดสวิตช์, ไม่มี migration, ไม่มี env ใหม่
- ไม่แก้ปัญหาเดิมที่ไม่เกี่ยว: `ack_expiry` ไม่ตรวจว่าผู้กดผูกบัญชีหรือไม่, โค้ดตายที่ `route.ts:313-316`

**สิ่งที่ถือว่าล้มเหลวแม้เทสต์ผ่าน**
- ผู้ใช้ที่ยังไม่ผูกบัญชีเห็นสต็อก/PO/พัสดุตอนสวิตช์เปิด
- ผู้ใช้แผนก B เห็น PO/พัสดุ/สต็อกของแผนก A, หรือ Vendor เห็น PO ของบริษัทอื่น
- ตอนสวิตช์ปิด ผู้ใช้เดิมถูกปฏิเสธหรือได้คำตอบต่างจากเดิม
- ผู้ใช้ที่ยังไม่ผูกบัญชีใช้คำสั่ง `id` / `ลงทะเบียน` ไม่ได้ (ต้องใช้ได้เสมอ เพราะเป็นทางผูกบัญชี)
- webhook ตอบ error แล้ว LINE ส่งซ้ำ (redelivery) จนตอบซ้ำหลายรอบ

## 3. ข้อจำกัด (constraints)

จาก handoff 21 ต.ค. และโค้ดจริง:
- ตรวจลายเซ็น (`validateSignature`) ก่อนเสมอ ก่อนอ่านหรือแตะอะไรทั้งหมด (`route.ts:121-129`) ห้ามเปลี่ยนลำดับ
- ห้ามห่อ try/catch รอบทั้ง batch ของ `Promise.all` (`:136-343`) — error ของ event หนึ่งยังต้องไหลไปที่ catch ชั้นนอกตามเดิม
- ห้ามเปลี่ยน SQL ของ postback ที่ไม่ใช้ผล (`:305-307`) และ SQL ของ `expiry_notification_logs`
- guard test `department-context.line-usage.test.ts` ห้าม `line-webhook/route.ts` อ้างชื่อ `resolveDepartmentForLineUser` โดยตรง ต้องเรียกผ่านฟังก์ชันใน `src/lib/line-liff-ordering.ts` (ไฟล์ที่ได้รับอนุญาต) ห้ามเพิ่มรายชื่อไฟล์ที่ได้รับอนุญาต
- `department-scope-coverage.test.ts`: ไฟล์ใน PENDING ห้าม import `scoped-db`/มี SQL ตารางแผนกแล้ว ต้องถอดรายการใน commit เดียวกับที่ย้ายโค้ด
- นโยบายเจ้าของ (บันทึกใน handoff): ไม่ผูกบัญชี LINE = ไม่ตอบสต็อก/PO/พัสดุ (เฉพาะตอนสวิตช์เปิด); ผูกแล้วแต่ไม่มีงาน = "ยังไม่มีงานที่ใช้งานได้ กรุณาแจ้งผู้ดูแลระบบ"
- ตัดสินใจในการสนทนานี้: Vendor กรองตามชื่อบริษัท (เจ้าของ 26 ต.ค.); เลือกแนวทาง B (เจ้าของ 26 ต.ค.)
- กฎโปรเจกต์: ห้ามรัน `npm run dev` (ชี้ production), ห้ามแตะ Neon จริง, ทดสอบด้วย PGlite เท่านั้น, ไม่ commit `ψ/`

## 5. การออกแบบ (ส่วนที่ตัดสินแล้ว)

### 5.1 ด่านตรวจ: `getLineBotAccess(lineUserId)` ใน `src/lib/line-liff-ordering.ts`
คืนผลแบบแยกกรณี (ไม่ใช่ boolean) เพื่อกันกลืนสถานะ:
- สวิตช์ปิด (`!departmentsFlagOn()`, อ่าน env อย่างเดียว) → `{ state: "legacy" }` **ไม่ยิง SQL เพิ่มเลย** (ต้องพิสูจน์ด้วยจำนวน statement เทียบ baseline). `legacy` ใช้กับสวิตช์ปิดเท่านั้น (แก้ตามคำตัดสินด้านล่าง)
- สวิตช์เปิด (ทั้งตอนแผนกพร้อมและยังไม่พร้อม): ไม่มี `lineUserId` → "ไม่ผูก"; `getLineLinkedUserAccess` (มีอยู่แล้ว) → `unlinked` / `inactive` → state เดียวกันคือ "ไม่ผูก" ; `active` เป็น **Vendor** → `{ state: "vendor", vendor }` **ไม่หาแผนกเลย ไม่ยิง SQL เพิ่ม** (Vendor ไม่ใช้สต็อก และ PO/พัสดุกรองด้วยชื่อบริษัท); `active` เป็นเจ้าหน้าที่ → ถ้า `departmentsReady()` เป็นเท็จ (probe หา schema ไม่เจอ หรือมี route ใดเรียก `markDepartmentsNotReady` ภายใน 60 วินาที) → `{ state: "degraded", role: <role ของบัญชี> }` ไม่หาแผนก; ถ้าพร้อม → เรียก `resolveDepartmentForLineUser(lineUserId, user.username)` → `null` = `no_work`; ได้ user → `{ state: "lab", role: <role ที่มีผลจริงในแผนก>, scope: {mode:"one", departmentId} }`
- error ของการหาแผนกที่เป็น 42P01/42703 (schema ยังไม่พร้อม) → `markDepartmentsNotReady(...)` แล้วคืน `{ state: "degraded", role }` (**ไม่ใช่** `legacy`); error อื่น rethrow (ไม่กลืน)
- `degraded` (สวิตช์เปิดแต่แผนกยังไม่พร้อม): บัญชีผูกแล้วและ active แต่ไม่รู้แผนก จึงตอบแบบไม่กรองแผนก (scope `{mode:"legacy"}` / actor `{kind:"legacy"}`); สต็อกใช้ได้ทุก role ของเจ้าหน้าที่; PO/พัสดุยังต้อง `isLabPurchasingRole(role)` (User/Operator/Technician ถูกปฏิเสธ); Vendor ไม่เข้า `degraded` (ได้ `vendor` ตามปกติ เห็นเฉพาะบริษัทตัวเอง)
- **คำตัดสิน (Ruling, final review 26 ต.ค.):** ร่างแรกของข้อนี้ให้ "ถอยเป็น legacy" ตอนแผนกยังไม่พร้อม แต่ใน webhook `legacy` แปลว่าไม่ตรวจตัวตนเลย ทำให้ตอนสวิตช์เปิด คนแปลกหน้าที่ไม่ผูกบัญชี (หรือ event ที่ไม่มี `source.userId`) เห็น PO/พัสดุ/สต็อกได้ ซึ่งขัดกับ "สิ่งที่ถือว่าล้มเหลว" ในหัวข้อ 2 (ผู้ใช้ที่ยังไม่ผูกบัญชีเห็นข้อมูลตอนสวิตช์เปิด). หัวข้อ 2 ชนะ: จึงเพิ่มสถานะ `degraded` แทนการถอยเป็น `legacy`
- ด่านคืน role ที่มีผลจริงมาให้ webhook: คำสั่ง PO/พัสดุตรวจ `isLabPurchasingRole(role)` ก่อนเรียกคำค้น (User → ข้อความปฏิเสธ); คำสั่งสต็อกไม่ตรวจ role (ทุก role ของเจ้าหน้าที่ใช้ได้); `state: "vendor"` ใช้สต็อกไม่ได้

### 5.2 คำค้นใหม่ `src/lib/line-bot-queries.ts`
- `findPurchaseOrderForLine(poNumber, actor)` และ `findShipmentForLine(trackingNo, actor)` รับ `actor` ที่ **บังคับ** (มี `assertActor` กันค่าผิด เหมือน `assertScope` ใน `bot-stock-queries.ts:22-27`)
- `actor`: `{ kind: "legacy" }` (SQL ข้อความเดิมทุกตัวอักษร: `SELECT * FROM purchase_orders WHERE po_number = ${n}` และ `SELECT * FROM shipments WHERE tracking_no = ${n}`), `{ kind: "lab", scope }` (เติม `andDept(scope)`), `{ kind: "vendor", vendor }` (เติม `AND vendor = ${vendor}` ไม่กรองแผนก)
- รายการสินค้าใน PO ดึงด้วย `po_id` จากแถวที่ผ่านการกรองแล้ว (เหมือนเว็บ)
- ไม่พบ/ไม่มีสิทธิ์ ตอบข้อความ "ไม่พบ..." เดียวกัน (ไม่บอกว่าบริษัทอื่น/แผนกอื่นมีอยู่)

### 5.3 การเปลี่ยนใน webhook (เล็กที่สุด)
- ข้อความสต็อก 3 จุด (`:190, :191, :200`): แทน `{mode:"legacy"}` ด้วย scope จากด่าน
- `PO-...` และเลขพัสดุ: เรียกฟังก์ชันใน `line-bot-queries.ts`
- ด่านทำงานเฉพาะเมื่อข้อความตรงกับคำสั่งสต็อก/PO/พัสดุ (ไม่ทำกับ `help`, `เมนู`, `order`, `เบิก`, `id`, `ลงทะเบียน`, `สั่งซื้อ`, ปฏิเสธ PO ของ Vendor ที่มีด่านของตัวเองอยู่แล้ว) — `id`/`ลงทะเบียน` ต้องใช้ได้ตอนยังไม่ผูกบัญชี
- กรณี `unlinked` / `inactive` / `no_work`: ตอบข้อความด้านล่าง ไม่ query ข้อมูล
- SQL ของ postback, `ack_expiry`, ลายเซ็น, โครง `Promise.all` ไม่เปลี่ยน

### 5.4 ข้อความ และค่าเริ่มต้น
ข้อความตามนโยบายเจ้าของ: ผูกแล้วแต่ไม่มีแผนก/แผนกถูกปิด → "ยังไม่มีงานที่ใช้งานได้ กรุณาแจ้งผู้ดูแลระบบ" ส่วนถ้อยคำข้อความอื่นเป็น **ร่างของผม** (คงความหมาย แก้ถ้อยคำได้):
- ผู้ใช้ไม่ผูก/บัญชีไม่ active ตอนสวิตช์เปิด: "บัญชี LINE นี้ยังไม่ได้ผูกกับบัญชี LabStock กรุณาผูกบัญชีก่อนใช้งานค่ะ (พิมพ์ \"id\" เพื่อดู LINE User ID)"
- `User` พิมพ์ PO/เลขพัสดุ: "บัญชีของคุณไม่มีสิทธิ์ดูใบสั่งซื้อและพัสดุผ่าน LINE ค่ะ"
- Vendor พิมพ์คำสั่งสต็อก: "คำสั่งสต็อกใช้ได้เฉพาะเจ้าหน้าที่แล็บค่ะ"
- Vendor พิมพ์ PO/เลขพัสดุของบริษัทอื่น: "ไม่พบ..." เหมือนไม่มีข้อมูล

### 5.5 การตัดสินของผมที่เจ้าของยังไม่ได้ยืนยัน (ขอให้ตรวจ)
1. **Vendor ที่ `users.vendor` ว่าง:** ได้ "ไม่พบ..." (เว็บตอบ 403 "Vendor profile is not configured" — ใน LINE ไม่เปิดเผยรายละเอียดนี้)
2. **Vendor ที่ไม่มีแถว `user_departments`:** ยังดู PO/พัสดุของบริษัทตัวเองใน LINE ได้ เพราะกรองด้วยชื่อบริษัทอย่างเดียว ไม่รั่วข้อมูลของใคร แต่ **หลวมกว่าเว็บ** (เว็บล็อกอินไม่ได้ ดู `docs/departments-rollout.md` หัวข้อ 11)
3. **guard test `department-context.line-usage.test.ts`:** ไม่ผ่อนกฎเดิม (webhook ยังห้ามอ้างชื่อ `resolveDepartmentForLineUser` และ ALLOWED ไม่เปลี่ยน); แก้ข้อความอธิบายที่ว่า "exactly one caller"; **เพิ่ม** การตรวจว่า `getLineBotAccess` ถูกอ้างจาก `line-webhook/route.ts` ที่เดียว (นอกจากไฟล์นิยาม) กันด่านรั่วไปใช้ที่อื่นโดยไม่ตั้งใจ
4. **ด่านไม่มี role check ในตัวเอง:** ปล่อยให้ webhook ตรวจ `isLabPurchasingRole` ต่อคำสั่ง เพื่อให้ `id`/`ลงทะเบียน`/สต็อกไม่ถูกบล็อกด้วย role
5. **(เพิ่มจากการตรวจแผน 26 ต.ค.) Vendor ไม่เห็น PO สถานะ `PENDING_MANAGER_REVIEW`:** เว็บซ่อนสถานะนี้จาก Vendor เสมอ (`purchase-orders/route.ts:63-64`, `[id]/route.ts:49`) LINE ต้องตรงกัน ไม่งั้นใบสั่งซื้อภายในที่ผู้จัดการยังไม่อนุมัติจะไปถึงบริษัทผู้ขาย (พัสดุไม่มีเงื่อนไขนี้ เหมือนเว็บ)
6. **คำค้น `purchase_order_items` อยู่ใน route ต่อไป** (ไม่ใช่ตารางแผนก; ดึงด้วย `po.id` ของแถวที่กรองแล้ว; ข้อความ SQL มีการเยื้องในตัว template จึงไม่ย้ายเพื่อให้ baseline ตรงทุกตัวอักษร)

## 6. การทดสอบ (ข้อกำหนด)
- **baseline legacy ก่อนแก้** (commit แรก, PGlite shim; mock `@neondatabase/serverless` ให้ webhook ใช้ shim; สร้างลายเซ็นจริงด้วย HMAC กับ `LINE_CHANNEL_SECRET` ทดสอบ): จับ SQL text/params/จำนวน/ลำดับ ของทุกทางที่ตอบข้อมูล ตอนสวิตช์ปิด + argument ที่ส่งเข้าฟังก์ชัน reply
- เทสต์สวิตช์เปิดบน PGlite (2 แผนก + Vendor 2 บริษัท): control query ว่ามีข้อมูลทั้งสองฝั่งจริง + positive control; unlinked/inactive/no_work ไม่ถึง query ข้อมูล; Vendor เห็นเฉพาะบริษัทตัวเองข้ามแผนก และใช้สต็อกไม่ได้ (ไม่ถึง query สต็อก); เจ้าหน้าที่ไม่เห็นข้ามแผนก; **role `User` (รวมกรณี role ระบบเป็น Manager แต่ถูก override เป็น User ในแผนก) ได้ข้อความปฏิเสธและไม่ถึง query PO/พัสดุ แต่ยังใช้สต็อกได้**; `id`/`ลงทะเบียน` ตอบทุกกรณี; เทสต์ mutation ของด่าน role (ลบการตรวจ `isLabPurchasingRole` ต้องมีเทสต์ล้ม)
- mutation: ลบ `andDept`, ลบ filter vendor, ข้ามด่าน, กลืน error, legacy ตายตัว — ต้องมีเทสต์ที่ล้มทุกจุด และรายงานจุดที่พิสูจน์ไม่ได้ตรง ๆ
- guard: line-usage test ยังผ่านโดยไม่แก้ ALLOWED; coverage test ผ่านทุก commit; แก้คอมเมนต์ใน line-usage test ที่ว่า "exactly one caller" ให้ตรงความจริง (ด่านใหม่อยู่ในไฟล์เดียวกัน)

## 7. ความเสี่ยงและสิ่งที่ยังไม่รู้
- ทดสอบได้เฉพาะ PGlite/mock **ยังไม่เคยรันบน Neon หรือ LINE จริง** (การต่อ fragment ว่างของ driver Neon และพฤติกรรมของ LINE ต้องตรวจตอนซ้อม)
- ตอนสวิตช์เปิดและฐานข้อมูลกระตุก: ด่านโยน error → batch ตอบ 500 → LINE อาจส่ง event ซ้ำ (redelivery) ตอบซ้ำได้ — เป็นพฤติกรรมเดิมของ webhook เมื่อ DB ล้ม ไม่ได้เกิดใหม่ แต่ต้องจดไว้
- สถานะแผนกเปลี่ยนระหว่างด่านกับคำค้น (แคช 60 วินาที): ด่านได้ `lab` แล้วคำค้นยังกรองด้วย `andDept` ของแผนกนั้น (ไม่ขึ้นกับสถานะพร้อม); ด่านได้ `degraded` คำค้นไม่กรองแผนกตามที่ตั้งใจ. ทั้งสองกรณีต้องผูกบัญชีแล้ว (ไม่มีทางที่คนไม่ผูกบัญชีเห็นข้อมูลตอนสวิตช์เปิด)
- **ข้อจำกัดที่รู้ (จดไว้ ไม่แก้ใน PR นี้):** (1) คำค้นของผู้ใช้ LINE คนเดียวที่เจอคอลัมน์หาย (42703) ทำให้ทั้ง instance ถูกตั้งเป็น "ยังไม่พร้อม" 60 วินาที (รูปแบบเดิมของ LIFF/`auth-utils`); probe ไม่ได้ตรวจ `user_departments.is_default`/`role` จึงอาจพร้อมตาม probe แต่ล้มตอนหาแผนก -> ช่วงนั้นเจ้าหน้าที่ที่ผูกบัญชีได้ข้อมูลไม่กรองแผนก (`degraded`); (2) ถ้าใช้บอทในห้องแชตกลุ่ม LINE คำตอบจะเห็นทุกคนในกลุ่ม (บอทดูแค่ `source.userId` ของผู้พิมพ์)
- จำนวนผู้ใช้ LINE จริงที่ผูกบัญชีแล้ว และ role override ต่อแผนกบน production: ไม่รู้จากข้อมูลที่มี
- Vendor ที่ไม่มี `user_departments` ล็อกอินเว็บไม่ได้อยู่แล้ว (เอกสารข้อ 11) แต่ใน LINE ยังไม่ทราบว่ามีกี่บัญชี
