# แผนเปิดระบบหลายแผนก (Departments) แบบปลอดภัย

เอกสารนี้เขียนให้เจ้าของระบบอ่าน ไม่ต้องเป็นโปรแกรมเมอร์
สถานะตอนเขียน: เป็นแผนเท่านั้น ยังไม่ได้ทำอะไรกับระบบจริง (production) เลย

## 1. ทำไปเพื่ออะไร

ตอนนี้ระบบมีห้องแล็บเดียว (ห้องปฏิบัติการเคมีคลินิก รหัส `CC`)
เราต้องการให้มีงานที่สอง (งานอณูชีววิทยา) ใช้ระบบเดียวกัน แต่ข้อมูลแยกกัน ไม่ปนกัน
และคนแต่ละแผนกเห็นเฉพาะข้อมูลของแผนกตัวเอง (Admin เลือก "ดูทุกงาน" ได้ แต่ดูได้อย่างเดียว)

หลักการ: โค้ดใหม่ถูกปิดไว้ด้วยสวิตช์ `DEPARTMENTS_ENABLED` ถ้าไม่ตั้งค่า ระบบทำงานเหมือนเดิมทุกอย่าง

## 2. ลำดับการทำงาน (ห้ามข้ามขั้น)

1. นำโค้ดขึ้นระบบจริงโดย **ปิดสวิตช์** (ไม่ตั้ง `DEPARTMENTS_ENABLED`) ระบบต้องทำงานเหมือนเดิม
2. ถ่าย snapshot ของฐานข้อมูล Neon เก็บไว้ก่อน (จุดย้อนกลับ)
3. ซ้อมก่อน: สร้าง branch ใหม่จากฐานข้อมูลจริงใน Neon แล้วรันไฟล์ `upgrade_v30` ถึง `upgrade_v34` ตามลำดับบน branch ซ้อมนั้นก่อน
   ดูว่าไม่มี error และจำนวนข้อมูลเท่าเดิม
4. รันไฟล์ v30 ถึง v34 บนฐานข้อมูลจริง (ผ่าน `node scripts/apply-migration.mjs <ไฟล์> --confirm-host=<host>`)
5. **ใส่แผนกให้ผู้ใช้ที่สมัครใหม่หลังรัน v30 ครั้งแรก** ขั้นนี้ **บังคับ** ทำทันทีก่อนเปิดสวิตช์
   ไม่งั้นผู้ใช้ที่ไม่มีแผนกจะเข้าระบบไม่ได้
   - **ห้ามรันไฟล์ v30 ซ้ำ** (แก้เมื่อ 2026-10-13 เดิมเขียนว่ารันซ้ำได้) เพราะส่วน backfill ของ v30
     ครอบคลุมแค่คู่ (username, department_id) ทำให้เกิดปัญหา 2 อย่าง (มีเทสต์พิสูจน์ใน
     `src/lib/department-migrations.db.test.ts`):
     (ก) ถ้ามีผู้ใช้ที่แผนกหลักไม่ใช่ CC จะ error `23505 user_departments_one_default_idx` ทันที
     (ข) ผู้ใช้ที่ถูกถอดออกจากทุกแผนกไปแล้วจะถูกใส่กลับ CC (การถอดสิทธิ์ต้องมีผลจริง
     ดู `src/lib/department-context.ts:77-80`)
   - ให้ใช้สคริปต์ครั้งเดียวที่เติมเฉพาะผู้ใช้ที่ **ไม่มีแถวสมาชิกแผนกเลย**
     (`INSERT INTO user_departments ... WHERE NOT EXISTS (SELECT 1 FROM user_departments x WHERE x.username = u.username)`)
     ต้องนับจำนวนก่อน/หลังและบันทึกรายชื่อผู้ที่ถูกเพิ่ม ทำได้เฉพาะ **ก่อนเปิดสวิตช์ครั้งแรก**
     หลังเปิดแล้ว ผู้ใช้ใหม่ต้องได้แถวสมาชิกจากหน้าสมัคร/สร้างผู้ใช้ (ข้อ 7) ไม่ใช่จากสคริปต์นี้
   - สคริปต์: `scripts/backfill-user-departments.mjs` (ตรรกะใน `scripts/backfill-user-departments-lib.mjs`, มีเทสต์ใน `src/lib/backfill-user-departments.db.test.ts`)
     - ไม่อ่านไฟล์ `.env` ต้องส่ง `DATABASE_URL` ทาง environment เอง และแสดงชื่อ host (ไม่แสดงรหัสผ่าน)
     - โหมดปกติ **อ่านอย่างเดียว** แสดงรายชื่อผู้ที่จะถูกเพิ่ม: `DATABASE_URL=... node scripts/backfill-user-departments.mjs`
     - เขียนจริงต้องมีทั้ง `--apply` และ `--confirm-host=<host>`: ทำใน transaction เดียว ตรวจจำนวนก่อน/หลัง และกันผู้ใช้ที่มีแผนกหลักซ้ำ ถ้าตรวจไม่ผ่านจะ rollback
     - เพิ่มเฉพาะผู้ใช้ที่ไม่มีแถวสมาชิกเลย เข้าแผนก CC เป็นแผนกหลัก (role ว่าง) ไม่แตะคนที่มีแผนกอยู่แล้ว รันซ้ำได้ (รอบสองไม่เพิ่มใคร)
     - ต้องขออนุมัติทุกครั้งก่อนรันบนฐานข้อมูลจริง และถ่าย snapshot ก่อน; ควรซ้อมบน Neon branch แยกก่อน
6. แก้ route (หน้า API) ทีละกลุ่มให้กรองตามแผนก จนรายการ `DEPARTMENT_SCOPE_PENDING`
   ในไฟล์ `src/lib/department-scope-coverage.test.ts` **ว่างเปล่า** (เทสต์จะเตือนเองถ้ายังค้าง)
7. ทำให้การสร้างผู้ใช้ใหม่/การสมัครสมาชิก เขียนแผนกลงตาราง `user_departments` ด้วย
   (ผู้ใช้ที่ไม่มีแผนกจะถูกปฏิเสธการเข้าระบบ)
8. เมื่อข้อ 6 และ 7 เสร็จเท่านั้น: รันไฟล์ล็อกกฎเข้มของข้อมูล (ถ้ามี) แล้วตั้ง `DEPARTMENTS_ENABLED=true`
   - หมายเลข: v35 = "ผู้ดูแลห้อง" (`user_departments.admin_slot` เพิ่มอย่างเดียว ไม่ล็อกอะไร รันก่อนเปิดสวิตช์ได้) มีไฟล์แล้ว;
     v36 = หัวกระดาษใบสั่งซื้อต่อแผนก (`lab_profile`, ดูหัวข้อ 10) มีไฟล์แล้วแต่ **ยังไม่ได้รัน**; ไฟล์ล็อกกฎเข้มถ้าจะทำให้ใช้ **v37 ขึ้นไป**
   แล้ว deploy ใหม่
9. จากนั้นจึงเริ่มสร้างข้อมูลในแผนกที่สอง (งานอณูชีววิทยา)

## 3. สิ่งที่อันตราย (ห้ามทำ)

- **ห้ามสร้างข้อมูลในแผนกที่สอง ก่อน PENDING ว่าง** — route ที่ยังไม่ถูกแก้จะไม่กรองแผนก
  ข้อมูลของสองแผนกจะโผล่ปนกัน และ Admin ที่ดูทุกงานอาจแก้ผิดแผนก
- **ห้ามเปิดสวิตช์ก่อนใส่แผนกให้ผู้ใช้ที่ยังไม่มีแผนก (ข้อ 5)** — ผู้ใช้ที่ไม่มีแผนกจะถูกล็อกออกจากระบบ
- **ห้ามรันไฟล์ v30 ซ้ำ** — error หรือคืนสิทธิ์ให้คนที่ถูกถอดไปแล้ว (รายละเอียดในข้อ 5)
  (Admin ยังเข้าได้เสมอ เพื่อมาแก้สมาชิกแผนก)
- **รหัสแผนก `LAB` ห้ามใช้เป็นรหัสแผนกเด็ดขาด** — `LAB-` เป็นคำนำหน้ารหัสวัสดุเดิมที่มีอยู่แล้ว
  ถ้าใช้ซ้ำรหัสจะชนกัน
- ห้ามรัน migration บนฐานข้อมูลจริงโดยยังไม่ซ้อมบน branch และยังไม่มี snapshot
- ห้ามลบตาราง/คอลัมน์ใหม่เพื่อ "ล้างให้สะอาด" โดยไม่ถามผู้ดูแลก่อน

## 4. ถ้าเกิดปัญหา จะย้อนกลับอย่างไร

เรียงจากเบาไปหนัก (ลองข้อบนก่อน):

1. **ปิดสวิตช์**: ลบหรือเปลี่ยน `DEPARTMENTS_ENABLED` ไม่ให้เป็น `true` แล้ว deploy ใหม่
   ระบบกลับไปทำงานแบบเดิมทันที ข้อมูลไม่หาย (นี่คือวิธีแรกที่ควรใช้เสมอ)
2. ถ้าปัญหามาจากโค้ด: ย้อน deploy ไปรุ่นก่อนหน้า (โค้ดเก่าไม่สนใจคอลัมน์ใหม่ จึงไม่พัง)
3. ถ้าต้องถอน migration: มีไฟล์ `*_rollback.sql` คู่กับแต่ละไฟล์ (เช่น `upgrade_v34_indexes_rollback.sql`)
   รันย้อนจากหมายเลขมากไปน้อย (v36 → v35 → v34 → ... → v31 → v30; v36 ใช้เฉพาะเมื่อถูกรันไปแล้ว) และทำเฉพาะเมื่อผู้ดูแลระบบตรวจแล้วว่าจำเป็น
   **ปิดสวิตช์และ deploy ก่อนรัน rollback SQL ทุกครั้ง** (ถ้าสวิตช์ยังเปิดอยู่ตอนถอน schema ระบบจะคิดว่าพร้อมตอนฐานข้อมูลกระตุก
   และบาง route จะตอบ 500 จนกว่าจะปิดสวิตช์)
4. ทางสุดท้าย: กู้จาก snapshot Neon ที่ถ่ายไว้ในขั้นที่ 2 (ข้อมูลที่เกิดหลัง snapshot จะหาย ต้องปรึกษาก่อนทำ)

## 5. ตรวจสอบว่าระบบทำงานถูกต้อง

หลังแต่ละขั้น ให้ตรวจ:

- ล็อกอินด้วยผู้ใช้ปกติ 1 คน และ Admin 1 คน ได้ตามปกติ
- จำนวนข้อมูลเดิม (วัสดุ, ประวัติ, ใบสั่งซื้อ) เท่าเดิมกับก่อนทำ
- ใน log ของระบบไม่มีข้อความ `[departments] DEPARTMENTS_ENABLED but schema not ready`
  (ถ้ามี แปลว่าเปิดสวิตช์แล้วแต่ฐานข้อมูลยังไม่พร้อม ระบบจะกลับไปใช้แบบเดิมเองและเตือนไว้)
- ถ้าเห็น `[departments] readiness check failed, not caching (...)` ใน log: นั่นคือการตรวจสคีมาล้มชั่วคราว (เช่น เครือข่าย/timeout)
  ข้อความท้ายบอกว่าระบบทำอย่างไร: `treating as ready (unconfirmed)` = instance ที่ยังไม่เคยยืนยันสคีมา **ถือว่าพร้อม**
  (ไม่ถอยไปแบบเดิม); `keeping ready` / `keeping not ready` = คงคำตอบที่เคยยืนยันไว้ แล้วทุกกรณีตรวจซ้ำทุก ~5 วินาที
  เหตุผล: การเปิดสวิตช์หมายความว่าเจ้าของยืนยันแล้วว่ารัน migration แล้ว จึงเลือกไม่ปล่อยให้ข้อมูลหลุดไม่กรองแผนก
  **ข้อเสียที่ยอมรับ (ตรวจแล้วด้วยการรันบน PGlite):** ถ้าเปิดสวิตช์ผิดลำดับ (ก่อนรัน migration ครบ) และฐานข้อมูลกระตุกพอดีบน instance ใหม่
  ระบบจะถือว่าพร้อมตลอดช่วงที่ตรวจไม่สำเร็จ (~5 วินาทีต่อรอบ) และ **ทุกคำขอ** ของ route ที่ใช้ตัวกรองแผนกจะตอบ 500 ตลอดช่วงนั้น (ไม่ใช่แค่ครั้งเดียว)
  ถ้าการตรวจล้มต่อเนื่องแต่คิวรีอื่นผ่าน อาจ 500 ต่อเนื่องไม่มีกำหนด (ไม่รู้จากข้อมูลที่มีว่าเกิดในโปรดักชันบ่อยแค่ไหน)
  แยกตามสถานะสคีมาตอนเปิดสวิตช์ผิดลำดับ:
  - ยังไม่รัน v30: เส้นล็อกอิน/session และ route ที่ผ่าน `getAuthenticatedUser` จะเจอ 42P01 แล้วเรียก `markDepartmentsNotReady` เอง จึงถอยเป็น legacy
    ส่วน route ที่ไม่ผ่านการยืนยันตัวตน เช่น register (GET/POST) จะตอบ 500 ตลอดช่วง ~5 วินาทีแรก
  - รัน v30 แล้วแต่ v31-v34 ยังไม่ครบ: `user_departments` มีแล้ว การยืนยันตัวตนจึงสำเร็จและไม่มีใครเรียก `markDepartmentsNotReady`
    ทุก route ที่กรองแผนก (ราว 41 ไฟล์ใต้ `src/app/api`) จะเจอ 42703 (ไม่มีคอลัมน์ `department_id`) และตอบ 500 จนกว่าการตรวจรอบถัดไปจะเห็นว่าสคีมาขาด
  ดังนั้น **ห้ามเปิดสวิตช์จนกว่า v30-v34 จะรันครบทุกไฟล์** (ตามลำดับในข้อ 2)
  route ที่เรียก `departmentsReady()` โดยตรง: register, users POST, account-status, station-auth, settings/barcodes,
  po-communication, room-route, pending-users approve, session/department, mobile/confirm (มีตัวดัก 42P01/42703 แล้วถอย legacy เอง)
  ตัวเลขผู้เรียก นับด้วย:
  `grep -rn "departmentsReady" src --include=*.ts --include=*.tsx | grep -v "\.test\." | grep -v "^src/lib/departments-flag.ts" | grep -v "import "`
  (ได้ 21 จุดใน 17 ไฟล์ ณ วันที่เขียน)
  สรุป: โหมดนี้เข้มกว่าเรื่องการกรองข้อมูล (ไม่มีข้อมูลรั่วข้ามแผนกหรือเขียนผิดแผนก) แต่บาง route ตอบ 500 แทนการถอยไป legacy ในช่วงสั้น ๆ (ไม่ใช่เข้มกว่าทุกจุด)
- ใน log ไม่มีข้อความ `user rejected: no department assignment` (ถ้ามี แปลว่ามีผู้ใช้ที่ยังไม่ถูกใส่แผนก
  ให้ใช้สคริปต์เติมแผนกครั้งเดียวในข้อ 5 หรือให้ Admin เพิ่มสมาชิกแผนกให้คนนั้น อย่ารัน v30 ซ้ำ)
- หลังเปิดสวิตช์: ผู้ใช้ที่มีหลายแผนกเห็นตัวสลับแผนก ผู้ใช้แผนกเดียวไม่เห็น
  และข้อมูลของแผนกที่สองไม่โผล่ในหน้าของแผนกแรก (ทดสอบด้วยข้อมูลทดลองบน branch ซ้อมก่อน)
- รันชุดทดสอบ `npx vitest run` ต้องผ่านทั้งหมดก่อน deploy ทุกครั้ง

## 6. สถานะการเบิก / รับเข้า / แจ้งเตือนของใกล้หมด

**ทำแล้ว** (มีผลเมื่อเปิดสวิตช์ `DEPARTMENTS_ENABLED` เท่านั้น):

- การเบิก การรับเข้า และการแจ้งเตือนของใกล้หมด กรองตามงานของผู้ใช้แล้ว
  ผู้ใช้จะเบิก/รับเข้าได้เฉพาะรายการของงานตัวเอง และแจ้งเตือนของใกล้หมดจะส่งถึงสมาชิกของงานนั้น
- โหมด "ดูทุกงาน" บันทึกการเบิก/รับเข้าไม่ได้ (ระบบตอบกลับว่าให้เลือกงานก่อน)
- รายการที่อยู่นอกงาน หรือรหัสที่ไม่มีอยู่จริง ได้ข้อความเดียวกันว่า "รายการนี้ไม่อยู่ในงานของคุณ"
  (จึงไม่ใบ้ว่ารหัสนั้นมีอยู่ในงานอื่นหรือไม่)
- ปิดสวิตช์ = ระบบทำงานเหมือนเดิมทุกอย่าง ไม่มี migration ใหม่ ไม่มีตัวแปร env ใหม่

**เงื่อนไขก่อนเปิดสวิตช์ (ห้ามข้าม):**

1. PR `feat/departments-mobile-auth` ทำแล้ว แต่ **ต้อง merge ก่อนเปิดสวิตช์**
   (ทำให้มือถือ/LIFF ที่เบิก–รับเข้า ใช้ "งานหลัก" (default) ของผู้อนุมัติ ยังไม่มีปุ่มเลือกงานบนมือถือ)
   ถ้าเปิดสวิตช์โดยยังไม่ merge มือถือ/LIFF จะตอบ error 500 ทุกครั้ง (ระบบปฏิเสธไว้ก่อนเพื่อความปลอดภัย แต่ใช้งานไม่ได้)

## 10. v36 หัวกระดาษใบสั่งซื้อต่อแผนก (PR-1: ไฟล์ migration / PR-2: โค้ดอ่านตามแผนก)

**คำสั่งตรวจ (อ่านอย่างเดียว) -- รันได้ก็ต่อเมื่อเจ้าของอนุญาต และก่อนซ้อมบน Neon branch แยก**

```sql
SELECT conname, contype, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'public.lab_profile'::regclass;
SELECT id, department_id FROM lab_profile;   -- เลือกเฉพาะ 2 คอลัมน์นี้เท่านั้น
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'lab_profile';
-- trigger / view / foreign key ที่อ้างถึง lab_profile (ยังไม่ทราบสภาพจริงบน Neon)
SELECT tgname FROM pg_trigger WHERE tgrelid = 'public.lab_profile'::regclass AND NOT tgisinternal;
SELECT c.relname FROM pg_depend d JOIN pg_rewrite r ON r.oid = d.objid JOIN pg_class c ON c.oid = r.ev_class
  WHERE d.refobjid = 'public.lab_profile'::regclass AND c.oid <> 'public.lab_profile'::regclass;
SELECT conname, conrelid::regclass FROM pg_constraint WHERE confrelid = 'public.lab_profile'::regclass;
```

**พฤติกรรมของ `vendor/shipments`**

- GET: ทุก role ต้องผ่าน `getDepartmentScope` (fail closed) ฝั่งแล็บ (Manager/Admin) กรองทั้ง `master_data` และ `shipments` ที่เงื่อนไข `JOIN` (โหมด legacy และโหมด "all" ไม่เติมอะไร SQL เหมือนเดิมทุกตัวอักษร); ฝั่ง Vendor ไม่กรองแผนก
- POST (โหมดแผนก): ตรวจ body ก่อน -> หา PO ของบริษัทนี้ (`SELECT department_id FROM purchase_orders WHERE po_number AND vendor`) -> ไม่พบ = 409 "This order is not eligible for shipment"; `department_id` ผิดรูปแบบ (ไม่ใช่จำนวนเต็มบวก) = 500 โดยไม่มีข้อความและไม่เริ่ม transaction -> ตรวจอายุคงเหลือ (shelf-life) ตามกฎของแผนก **ของ PO** -> transaction
- **ความต่างที่ตั้งใจ (เฉพาะโหมดแผนก):** PO ที่ไม่พบ จะได้ 409 "not eligible" **ก่อน** 409 shelf-life (ในโหมด legacy ยังเป็นลำดับเดิม: shelf-life ก่อน ไม่มี query เพิ่ม)
- CTE `po` มีเงื่อนไขแผนกของ PO ซ้ำอีกชั้น กัน PO ย้ายแผนกระหว่างอ่านกับเขียน (ได้ 409 และไม่เขียนอะไร)
- โหมด "all" เขียนไม่ได้: 409 `DEPARTMENT_READ_ONLY` ก่อนส่ง SQL ใด ๆ
- ทุก catch ตรวจ `isDepartmentScopeFailure` ก่อน และตอบผ่าน `toApiError` (ไม่เผยชื่อผู้ใช้ใน error)

**จุดที่ตั้งใจไม่กรองแผนก (ทุกจุดมีคอมเมนต์ในโค้ด)**

- CTE `existing` (ตัวกัน POST ซ้ำ) -- unique index ของ v25 (`client_request_id` / `request_fingerprint`) ยังเป็นระดับระบบ ถ้ากรองจะกลายเป็น 500 แทนที่จะตอบ `duplicate:true`

## 12. กลุ่ม 3: การแจ้งเตือน expiring-soon / vendor-low-stock / weekly-stock-summary (ทำแล้ว)

**นโยบาย (เจ้าของตัดสินแล้ว)**

**สิทธิ์เรียก / ขอบเขต**

- ชื่อ secret, ชื่อ header และลำดับการตรวจของแต่ละ route **ไม่เปลี่ยน** (expiring-soon: `EXPIRY_NOTIFICATION_CRON_SECRET` + `x-cron-secret`, ผู้ใช้ Admin เท่านั้น; vendor-low-stock: `LOW_STOCK_NOTIFICATION_CRON_SECRET` + `x-cron-secret`, Admin/Manager; weekly: `WEEKLY_STOCK_NOTIFICATION_CRON_SECRET` หรือ `CRON_SECRET` ทั้ง `x-cron-secret` และ `Authorization: Bearer`, Admin/Manager) เปลี่ยนแค่ค่าที่ได้จากการตรวจสิทธิ์: secret ถูก = `{ mode: "all" }` (หรือ `legacy` ตอนสวิตช์ปิด), ผู้ใช้ที่ล็อกอิน = scope ของตัวเอง (Manager ห้องเดียวกดแล้วได้เฉพาะสินค้าของห้องตัวเอง)

**พฤติกรรมแต่ละ route (โหมดแผนก)**

- `vendor-low-stock`: ผู้รับมีแต่ Vendor จึงไม่ดู `user_departments`; กรองเฉพาะสินค้า (`master_data`) ตาม scope. cron ได้ทุกแผนก

- `weekly-stock-summary`: staff ได้สรุป **ต่อแผนก** และ **ส่งแม้แผนกนั้นไม่มีรายการ** (เหมือน legacy ที่ส่งเสมอ) แต่เฉพาะแผนกที่ผู้รับเป็นสมาชิก. **Vendor ในโหมด "one" (Manager ห้องเดียวกด) ได้เฉพาะของ vendor ตัวเองใน "แผนกที่ scope นั้นเห็น"** (ไม่ใช่ทุกแผนก) ส่วน cron ได้ทุกแผนก -- เป็นพฤติกรรมที่ตั้งใจ มีเทสต์ล็อกไว้. สินค้าที่ `department_id` ผิดรูป/ว่างไม่ถึง staff คนใด (Vendor ยังได้ตามนโยบายข้อ 3)

- **โหมด degraded** (สวิตช์เปิด แต่แผนกยังไม่พร้อม: probe หา schema ไม่เจอ, มี route ใดเรียก `markDepartmentsNotReady` ภายใน 60 วินาที, หรือเจอ 42P01/42703 ตอนหาแผนก): ยังต้องผูกบัญชีที่ active อยู่ (ไม่ผูก/ไม่ active/ไม่มี `source.userId` -> ข้อความให้ผูกบัญชี ไม่ query ข้อมูล); Vendor เห็นเฉพาะของบริษัทตัวเองเหมือนเดิม; เจ้าหน้าที่ได้ข้อมูล **ไม่กรองแผนก** (เพราะไม่รู้แผนก) สต็อกใช้ได้ทุก role ส่วน PO/พัสดุยังต้องเป็น Admin/Manager (role ของบัญชี). คำตัดสินจาก final review: "คนไม่ผูกบัญชีต้องไม่เห็นข้อมูลตอนสวิตช์เปิด" (spec หัวข้อ 2) ชนะ "ถอยเป็น legacy" ในร่างแรกของ spec 5.1
- webhook ไม่อ้าง `resolveDepartmentForLineUser` โดยตรง (ตามที่ `department-context.line-usage.test.ts` บังคับ) และ SQL ของ postback, `ack_expiry`, `expiry_notification_logs`, การตรวจลายเซ็น, โครง `Promise.all` ไม่เปลี่ยน. คำค้นรายการสินค้าใน PO (`purchase_order_items`) อยู่ใน route ต่อไป ดึงด้วย `po.id` ของแถวที่ผ่านการกรองแล้ว
- **สวิตช์ปิด:** ทางเดิมไม่เปลี่ยน -- webhook เช็ก `departmentsFlagOn()` (ไม่แตะฐานข้อมูล) แล้วใช้ access แบบ `legacy` ซึ่งได้ scope `{ mode: "legacy" }` และ actor `{ kind: "legacy" }` (SQL `SELECT * FROM purchase_orders WHERE po_number = ...` / `SELECT * FROM shipments WHERE tracking_no = ...` ข้อความเดิม). ข้อความ SQL + params + จำนวน statement + ลำดับ + คำตอบที่ส่งเข้า reply เหมือนเดิมทุกไบต์: `line-webhook.legacy.test.ts` เทียบกับ `line-webhook.legacy-baseline.json` ที่บันทึกจากโค้ดเดิมก่อนแก้ (ห้ามสร้างใหม่ยกเว้นตั้งใจด้วย `UPDATE_LINE_WEBHOOK_BASELINE=1`)

## มือถือ lookup ต้องล็อกอิน (2026-10-29)

ถอด `src/app/api/mobile/lookup/route.ts` ออกจาก `DEPARTMENT_SCOPE_PENDING` (**2 -> 1**, นับจริงจาก `department-scope-coverage.test.ts`): ที่เหลือ 1 คือ `src/app/api/auth/register/route.ts` (ตั้งใจค้าง). ไม่มี migration, ไม่มี env ใหม่; สวิตช์ `DEPARTMENTS_ENABLED` ยังปิด

**พฤติกรรมใหม่ของ `GET /api/mobile/lookup`:**

- ต้องล็อกอินก่อนเสมอ ไม่ล็อกอินได้ 401 (ตรวจตัวตนก่อนเรื่องแผนกทุกกรณี แม้สวิตช์ปิด)
- ผู้เรียกจะเห็นเฉพาะรายการและ lot ของ "งานหลัก (default)" ของตัวเอง ใช้ฟังก์ชันเดียวกับ `/api/mobile/confirm` จึงตรงกันเสมอ ไม่มีโหมด "ทุกงาน" และไม่รับงานจากคำขอ
- ถ้าหน้า LIFF ส่งหัวข้อ `X-Line-Id-Token` มา ระบบใช้ตัวตน LINE **อย่างเดียว** (ชนะ cookie เว็บ); token ผิด/หมดอายุ/บัญชียังไม่ผูก = 401 ไม่ย้อนไปใช้ cookie. ไม่มีหัวข้อ = ใช้ session ของเว็บ
- Vendor ได้ 403; ผู้ใช้ผ่าน LINE ที่ไม่มีงานใช้งานได้ ได้ 403 (ข้อความเดียวกับ confirm); session ที่หมดอายุ/ถูกเพิกถอน/ไม่มีงานได้ 401 (ให้ไปล็อกอินใหม่)
  - **ข้อควรรู้:** ผู้ใช้ที่ล็อกอินเว็บแล้วแต่ไม่มีงาน (แผนก) ที่ใช้งานได้ จะได้ 401 แล้วถูกส่งไปหน้า `/login` และ **ล็อกอินใหม่ก็ไม่หาย** ต้องให้ผู้ดูแลเพิ่มสมาชิกแผนกให้ผู้ใช้คนนั้น (ตอนนี้ยังไม่มีหน้าจอหรือ API สำหรับทำเรื่องนี้ ต้องแก้ฐานข้อมูลโดยตรง และต้องถามเจ้าของระบบก่อนทุกครั้ง)
- สวิตช์ปิดหรือยังไม่มี schema: ยังต้องล็อกอิน แต่ได้ข้อมูลไม่กรองแผนกเหมือนเดิม
- ถ้าคอลัมน์ LINE ในฐานข้อมูลยังไม่มี ทางเข้าด้วย LINE ตอบ HTTP 400 (เหมือน confirm)
- คำตอบมี `Cache-Control: no-store`; error 500 เป็นข้อความตายตัว ไม่มีชื่อผู้ใช้หรือ SQL
- **ผลที่ผู้ใช้เห็น:** มือถือเครื่องกลางที่เปิด `/mobile` แล้วกรอกแค่ PIN ตอนยืนยันจะใช้ไม่ได้อีก ทุกคนต้องล็อกอินก่อน (หน้าเว็บ `/mobile` เด้งไป `/login`; หลังล็อกอินระบบพาไป `/dashboard` เสมอ ไม่ได้เพิ่มทางกลับหน้ามือถือ)

**ข้อจำกัดที่รู้ (จดไว้ ไม่แก้ใน PR นี้):**

- บนเว็บ `/mobile` คนที่กดยืนยันคือ username+PIN ที่พิมพ์ตอนยืนยัน ซึ่งอาจไม่ใช่คนที่ล็อกอินอยู่ ถ้าสองคนมีงานหลักต่างกัน confirm จะปฏิเสธ (`ITEM_NOT_IN_DEPARTMENT` ปลอดภัย ไม่รั่วข้อมูล) แต่อาจทำให้ผู้ใช้งง; ไม่ได้แก้ `confirm`
- รูปแบบบาร์โค้ด: lookup ยังเรียก `loadRuntimeBarcodePatterns({ mode: "all" })` (เห็นรูปแบบบาร์โค้ดของทุกงานตามเดิม ไม่มีรายการสต็อกรั่ว); ตัว `barcode-runtime.ts` ออกจาก PENDING ไปแล้วตั้งแต่กลุ่มบาร์โค้ด
- LINE ID token หมดอายุได้ ถ้าโหลด lookup ซ้ำตอนใกล้สิ้นสุดการใช้งาน LIFF อาจได้ 401 (ให้เปิดหน้า LIFF ใหม่) เหมือน confirm ปัจจุบัน
- ทุกครั้งที่ LIFF เรียก lookup จะเรียก API ตรวจ token ของ LINE; **หลัง deploy หน้า LIFF ที่เปิดค้างด้วย JS เก่าจะได้ 401 จนกว่าจะโหลดหน้าใหม่**
- ตอนสวิตช์แผนกเปิดแต่ตรวจ schema ไม่ผ่าน ระบบจะถอยไปโหมดเก่า (ไม่กรองแผนก) ชั่วคราวสำหรับคนที่ล็อกอินแล้ว (คนไม่ล็อกอินยังได้ 401) รูปแบบเดียวกับ confirm และ line-webhook (ดูหมายเหตุเดิมแถวหัวข้อ LINE webhook ด้านบน)

  - (ข) ล็อกอินแล้ว -> รายการสินค้าต้องแสดง
  - (ค) เปิด LIFF ใน LINE -> โหลดรายการได้ และกดยืนยันได้

**กฎเดิมยังอยู่:** ห้ามสร้างข้อมูลงานที่สองจนกว่า `DEPARTMENT_SCOPE_PENDING` จะว่าง (ตอนนี้เหลือแค่ `auth/register`).
