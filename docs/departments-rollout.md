# แผนเปิดระบบหลายแผนก (Departments) แบบปลอดภัย

เอกสารนี้เขียนให้เจ้าของระบบอ่าน ไม่ต้องเป็นโปรแกรมเมอร์
สถานะตอนเขียน: เป็นแผนเท่านั้น ยังไม่ได้ทำอะไรกับระบบจริง (production) เลย

## 1. ทำไปเพื่ออะไร

ตอนนี้ระบบมีห้องแล็บเดียว (ห้องปฏิบัติการเคมีคลินิก รหัส `CC`)
เราต้องการให้มีงานที่สอง (งานอณูชีววิทยา) ใช้ระบบเดียวกัน แต่ข้อมูลแยกกัน ไม่ปนกัน
และคนแต่ละแผนกเห็นเฉพาะข้อมูลของแผนกตัวเอง (Admin เลือก "ดูทุกงาน" ได้ แต่ดูได้อย่างเดียว)

หลักการ: โค้ดใหม่ถูกปิดไว้ด้วยสวิตช์ `DEPARTMENTS_ENABLED` ถ้าไม่ตั้งค่า ระบบทำงานเหมือนเดิมทุกอย่าง

## 2. ลำดับการทำงาน (ห้ามข้ามขั้น)

1. นำโค้ดขึ้นระบบจริงโดย **ปิดสวิตช์** (ไม่ตั้ง `DEPARTMENTS_ENABLED`) ระบบต้องทำงานเหมือนเดิม
2. ถ่าย snapshot ของฐานข้อมูล Neon เก็บไว้ก่อน (จุดย้อนกลับ)
3. ซ้อมก่อน: สร้าง branch ใหม่จากฐานข้อมูลจริงใน Neon แล้วรันไฟล์ `upgrade_v30` ถึง `upgrade_v34` ตามลำดับบน branch ซ้อมนั้นก่อน
   ดูว่าไม่มี error และจำนวนข้อมูลเท่าเดิม
4. รันไฟล์ v30 ถึง v34 บนฐานข้อมูลจริง (ผ่าน `node scripts/apply-migration.mjs <ไฟล์> --confirm-host=<host>`)
5. **ใส่แผนกให้ผู้ใช้ที่สมัครใหม่หลังรัน v30 ครั้งแรก** ขั้นนี้ **บังคับ** ทำทันทีก่อนเปิดสวิตช์
   ไม่งั้นผู้ใช้ที่ไม่มีแผนกจะเข้าระบบไม่ได้
   - **ห้ามรันไฟล์ v30 ซ้ำ** (แก้เมื่อ 2026-10-13 เดิมเขียนว่ารันซ้ำได้) เพราะส่วน backfill ของ v30
     ครอบคลุมแค่คู่ (username, department_id) ทำให้เกิดปัญหา 2 อย่าง (มีเทสต์พิสูจน์ใน
     `src/lib/department-migrations.db.test.ts`):
     (ก) ถ้ามีผู้ใช้ที่แผนกหลักไม่ใช่ CC จะ error `23505 user_departments_one_default_idx` ทันที
     (ข) ผู้ใช้ที่ถูกถอดออกจากทุกแผนกไปแล้วจะถูกใส่กลับ CC (การถอดสิทธิ์ต้องมีผลจริง
     ดู `src/lib/department-context.ts:77-80`)
   - ให้ใช้สคริปต์ครั้งเดียวที่เติมเฉพาะผู้ใช้ที่ **ไม่มีแถวสมาชิกแผนกเลย**
     (`INSERT INTO user_departments ... WHERE NOT EXISTS (SELECT 1 FROM user_departments x WHERE x.username = u.username)`)
     ต้องนับจำนวนก่อน/หลังและบันทึกรายชื่อผู้ที่ถูกเพิ่ม ทำได้เฉพาะ **ก่อนเปิดสวิตช์ครั้งแรก**
     หลังเปิดแล้ว ผู้ใช้ใหม่ต้องได้แถวสมาชิกจากหน้าสมัคร/สร้างผู้ใช้ (ข้อ 7) ไม่ใช่จากสคริปต์นี้
   - สคริปต์: `scripts/backfill-user-departments.mjs` (ตรรกะใน `scripts/backfill-user-departments-lib.mjs`, มีเทสต์ใน `src/lib/backfill-user-departments.db.test.ts`)
     - ไม่อ่านไฟล์ `.env` ต้องส่ง `DATABASE_URL` ทาง environment เอง และแสดงชื่อ host (ไม่แสดงรหัสผ่าน)
     - โหมดปกติ **อ่านอย่างเดียว** แสดงรายชื่อผู้ที่จะถูกเพิ่ม: `DATABASE_URL=... node scripts/backfill-user-departments.mjs`
     - เขียนจริงต้องมีทั้ง `--apply` และ `--confirm-host=<host>`: ทำใน transaction เดียว ตรวจจำนวนก่อน/หลัง และกันผู้ใช้ที่มีแผนกหลักซ้ำ ถ้าตรวจไม่ผ่านจะ rollback
     - เพิ่มเฉพาะผู้ใช้ที่ไม่มีแถวสมาชิกเลย เข้าแผนก CC เป็นแผนกหลัก (role ว่าง) ไม่แตะคนที่มีแผนกอยู่แล้ว รันซ้ำได้ (รอบสองไม่เพิ่มใคร)
     - ต้องขออนุมัติทุกครั้งก่อนรันบนฐานข้อมูลจริง และถ่าย snapshot ก่อน; ควรซ้อมบน Neon branch แยกก่อน
6. แก้ route (หน้า API) ทีละกลุ่มให้กรองตามแผนก จนรายการ `DEPARTMENT_SCOPE_PENDING`
   ในไฟล์ `src/lib/department-scope-coverage.test.ts` **ว่างเปล่า** (เทสต์จะเตือนเองถ้ายังค้าง)
7. ทำให้การสร้างผู้ใช้ใหม่/การสมัครสมาชิก เขียนแผนกลงตาราง `user_departments` ด้วย
   (ผู้ใช้ที่ไม่มีแผนกจะถูกปฏิเสธการเข้าระบบ)
8. เมื่อข้อ 6 และ 7 เสร็จเท่านั้น: รันไฟล์ล็อกกฎเข้มของข้อมูล (ถ้ามี) แล้วตั้ง `DEPARTMENTS_ENABLED=true`
   - หมายเลข: v35 = "ผู้ดูแลห้อง" (`user_departments.admin_slot` เพิ่มอย่างเดียว ไม่ล็อกอะไร รันก่อนเปิดสวิตช์ได้) มีไฟล์แล้ว;
     v36 = หัวกระดาษใบสั่งซื้อต่อแผนก (`lab_profile`, ดูหัวข้อ 10) มีไฟล์แล้วแต่ **ยังไม่ได้รัน**; ไฟล์ล็อกกฎเข้มถ้าจะทำให้ใช้ **v37 ขึ้นไป**
   แล้ว deploy ใหม่
9. จากนั้นจึงเริ่มสร้างข้อมูลในแผนกที่สอง (งานอณูชีววิทยา)

## 3. สิ่งที่อันตราย (ห้ามทำ)

- **ห้ามสร้างข้อมูลในแผนกที่สอง ก่อน PENDING ว่าง** — route ที่ยังไม่ถูกแก้จะไม่กรองแผนก
  ข้อมูลของสองแผนกจะโผล่ปนกัน และ Admin ที่ดูทุกงานอาจแก้ผิดแผนก
- **ห้ามเปิดสวิตช์ก่อนใส่แผนกให้ผู้ใช้ที่ยังไม่มีแผนก (ข้อ 5)** — ผู้ใช้ที่ไม่มีแผนกจะถูกล็อกออกจากระบบ
- **ห้ามรันไฟล์ v30 ซ้ำ** — error หรือคืนสิทธิ์ให้คนที่ถูกถอดไปแล้ว (รายละเอียดในข้อ 5)
  (Admin ยังเข้าได้เสมอ เพื่อมาแก้สมาชิกแผนก)
- **รหัสแผนก `LAB` ห้ามใช้เป็นรหัสแผนกเด็ดขาด** — `LAB-` เป็นคำนำหน้ารหัสวัสดุเดิมที่มีอยู่แล้ว
  ถ้าใช้ซ้ำรหัสจะชนกัน
- ห้ามรัน migration บนฐานข้อมูลจริงโดยยังไม่ซ้อมบน branch และยังไม่มี snapshot
- ห้ามลบตาราง/คอลัมน์ใหม่เพื่อ "ล้างให้สะอาด" โดยไม่ถามผู้ดูแลก่อน

## 4. ถ้าเกิดปัญหา จะย้อนกลับอย่างไร

เรียงจากเบาไปหนัก (ลองข้อบนก่อน):

1. **ปิดสวิตช์**: ลบหรือเปลี่ยน `DEPARTMENTS_ENABLED` ไม่ให้เป็น `true` แล้ว deploy ใหม่
   ระบบกลับไปทำงานแบบเดิมทันที ข้อมูลไม่หาย (นี่คือวิธีแรกที่ควรใช้เสมอ)
2. ถ้าปัญหามาจากโค้ด: ย้อน deploy ไปรุ่นก่อนหน้า (โค้ดเก่าไม่สนใจคอลัมน์ใหม่ จึงไม่พัง)
3. ถ้าต้องถอน migration: มีไฟล์ `*_rollback.sql` คู่กับแต่ละไฟล์ (เช่น `upgrade_v34_indexes_rollback.sql`)
   รันย้อนจากหมายเลขมากไปน้อย (v36 → v35 → v34 → ... → v31 → v30; v36 ใช้เฉพาะเมื่อถูกรันไปแล้ว) และทำเฉพาะเมื่อผู้ดูแลระบบตรวจแล้วว่าจำเป็น
4. ทางสุดท้าย: กู้จาก snapshot Neon ที่ถ่ายไว้ในขั้นที่ 2 (ข้อมูลที่เกิดหลัง snapshot จะหาย ต้องปรึกษาก่อนทำ)

## 5. ตรวจสอบว่าระบบทำงานถูกต้อง

หลังแต่ละขั้น ให้ตรวจ:

- ล็อกอินด้วยผู้ใช้ปกติ 1 คน และ Admin 1 คน ได้ตามปกติ
- จำนวนข้อมูลเดิม (วัสดุ, ประวัติ, ใบสั่งซื้อ) เท่าเดิมกับก่อนทำ
- ใน log ของระบบไม่มีข้อความ `[departments] DEPARTMENTS_ENABLED but schema not ready`
  (ถ้ามี แปลว่าเปิดสวิตช์แล้วแต่ฐานข้อมูลยังไม่พร้อม ระบบจะกลับไปใช้แบบเดิมเองและเตือนไว้)
- ใน log ไม่มีข้อความ `user rejected: no department assignment` (ถ้ามี แปลว่ามีผู้ใช้ที่ยังไม่ถูกใส่แผนก
  ให้ใช้สคริปต์เติมแผนกครั้งเดียวในข้อ 5 หรือให้ Admin เพิ่มสมาชิกแผนกให้คนนั้น อย่ารัน v30 ซ้ำ)
- หลังเปิดสวิตช์: ผู้ใช้ที่มีหลายแผนกเห็นตัวสลับแผนก ผู้ใช้แผนกเดียวไม่เห็น
  และข้อมูลของแผนกที่สองไม่โผล่ในหน้าของแผนกแรก (ทดสอบด้วยข้อมูลทดลองบน branch ซ้อมก่อน)
- รันชุดทดสอบ `npx vitest run` ต้องผ่านทั้งหมดก่อน deploy ทุกครั้ง

## 6. สถานะการเบิก / รับเข้า / แจ้งเตือนของใกล้หมด

**ทำแล้ว** (มีผลเมื่อเปิดสวิตช์ `DEPARTMENTS_ENABLED` เท่านั้น):

- การเบิก การรับเข้า และการแจ้งเตือนของใกล้หมด กรองตามงานของผู้ใช้แล้ว
  ผู้ใช้จะเบิก/รับเข้าได้เฉพาะรายการของงานตัวเอง และแจ้งเตือนของใกล้หมดจะส่งถึงสมาชิกของงานนั้น
- โหมด "ดูทุกงาน" บันทึกการเบิก/รับเข้าไม่ได้ (ระบบตอบกลับว่าให้เลือกงานก่อน)
- รายการที่อยู่นอกงาน หรือรหัสที่ไม่มีอยู่จริง ได้ข้อความเดียวกันว่า "รายการนี้ไม่อยู่ในงานของคุณ"
  (จึงไม่ใบ้ว่ารหัสนั้นมีอยู่ในงานอื่นหรือไม่)
- ปิดสวิตช์ = ระบบทำงานเหมือนเดิมทุกอย่าง ไม่มี migration ใหม่ ไม่มีตัวแปร env ใหม่

**เงื่อนไขก่อนเปิดสวิตช์ (ห้ามข้าม):**

1. PR `feat/departments-mobile-auth` ทำแล้ว แต่ **ต้อง merge ก่อนเปิดสวิตช์**
   (ทำให้มือถือ/LIFF ที่เบิก–รับเข้า ใช้ "งานหลัก" (default) ของผู้อนุมัติ ยังไม่มีปุ่มเลือกงานบนมือถือ)
   ถ้าเปิดสวิตช์โดยยังไม่ merge มือถือ/LIFF จะตอบ error 500 ทุกครั้ง (ระบบปฏิเสธไว้ก่อนเพื่อความปลอดภัย แต่ใช้งานไม่ได้)
2. การเบิก การรับเข้า และการแจ้งเตือนของใกล้หมด ต้อง merge **พร้อมกันใน PR เดียว** ห้าม deploy ครึ่งทาง
   ถ้าต้องย้อนกลับ ให้ย้อนทั้งชุด
3. ก่อนสร้างข้อมูลงานที่สอง ให้ตรวจความสอดคล้องของข้อมูลสต็อกกับรายการวัสดุ ผลต้องได้ **0**:

   `SELECT count(*) FROM inventory i JOIN master_data m ON m.item_id = i.item_id WHERE i.department_id <> m.department_id;`

   ถ้าไม่ใช่ 0 แถวสต็อกที่ไม่ตรงนั้นจะ "หายจากการเบิก" แบบเงียบ ๆ (เบิกไม่ได้ ขึ้นว่าไม่พบรอบรับเข้า) ต้องแก้ข้อมูลก่อน

**ข้อควรรู้ (ผลข้างเคียงที่ตั้งใจ/ยอมรับได้):**

- Admin ที่สร้างหลังรัน v30 ครั้งสุดท้าย (หรือไม่มีแถวสมาชิกของงานนั้น) จะไม่ได้แจ้งเตือนของใกล้หมดของงานนั้น
  ทั้งที่ยังล็อกอินได้ แก้โดยให้เพิ่มสมาชิกงานให้คนนั้น
- Vendor ได้แจ้งเตือนของใกล้หมดของทุกงาน แต่เฉพาะสินค้าของบริษัทตัวเอง (ตั้งใจ)
- หน้ามือถือส่วนค้นหารายการ (`/api/mobile/lookup`) ไม่ต้องล็อกอิน และยังคืนรายการของทุกงาน (ยังอยู่ใน `DEPARTMENT_SCOPE_PENDING`)
  ผู้ใช้มือถือเห็นรายการของงานอื่นได้ แต่ยืนยันเบิก/รับเข้าไม่ได้ (ได้ข้อความปฏิเสธ) ซึ่งปลอดภัยและยอมรับได้ชั่วคราว
  ต้องออกแบบใหม่เป็นงานต่อไป
- `/api/usage` (รายการที่ป้อนช่องเลือกน้ำยาในหน้า Analysis) ยังไม่กรองตามงาน แท็บ "รายน้ำยา" จึงยังแสดงรหัสรายการของงานอื่นได้
  แต่เมื่อเลือกจะได้ 404 (`/api/usage/item` กรองตามงานแล้ว) จนกว่าจะย้าย `/api/usage`
- การแจ้งเตือน "รับเข้า/เบิก" (STOCK_RECEIVED/STOCK_DISPENSED) ไม่ได้ส่งถึงใครอยู่แล้ว ไม่เปลี่ยนแปลง
- ตัวเขียนสต็อก 4 ตัวถูกย้ายมากรองตามงานแล้ว ได้แก่ งานนับสต็อก (count-work-orders และ 4 route ของมัน),
  การยืม-คืนน้ำยา (reagent-loans), inventory/reconcile และการรับ/ยกเลิก vendor shipment ฝั่งแล็บ (vendor/shipments/[id])
  ทำให้ `DEPARTMENT_SCOPE_PENDING` ลดจาก 50 เหลือ 46 รายการ (ตรวจนับจริงใน `department-scope-coverage.test.ts` เมื่อ 2026-10-13 ได้ 46 รายการ ไม่ใช่ 45 ที่เคยเขียนไว้) ที่ยังไม่ได้ย้ายและยังเขียนลงงาน CC ตามค่าเริ่มต้นของคอลัมน์
  จึง **ห้ามใช้ในงานที่สองจนกว่าจะย้าย** เช่น vendor/shipments (POST), purchase-orders, master, settings
  ข้อนี้คงกฎเดิมไว้: ห้ามสร้างข้อมูลงานที่สองก่อน `DEPARTMENT_SCOPE_PENDING` ว่าง

**ข้อจำกัดที่ทราบหลังย้ายตัวเขียนสต็อก 4 ตัว (ยอมรับชั่วคราว):**

- งานที่สองรับของจาก vendor shipment ยังไม่ได้ จนกว่าจะย้าย `vendor/shipments` (POST) เพราะ POST ยังสร้างรายการส่งของลงงาน CC เสมอ
  ผู้ใช้งานที่สองที่กดรับของที่เป็นของงาน CC จะได้ 404 (ปลอดภัย ปฏิเสธไว้ก่อน)
- index เดิม `idx_count_work_orders_one_open_per_owner_job` ยังเป็นแบบทั้งระบบ (ไม่แยกงาน) จึงยังกันไม่ให้เจ้าของคนเดียวกัน

- `GET/PATCH /api/purchase-orders/[id]`: ค้นหาด้วย id และ `po_number` กรองตามแผนก (PO ของแผนกอื่น = 404); `current_stock_qty` นับเฉพาะ inventory ของแผนกที่ดู; ทุก action ของ Lab ใน PATCH ใช้ scope เดียวกัน; จัดการ `DEPARTMENT_NOT_FOUND` / `DEPARTMENT_READ_ONLY` เป็น 404 / 409 (ไม่ใช่ 500) ทั้ง GET และ PATCH

- `po_seq` (เลขที่ PO) -- เป็นลำดับเดียวทั้งระบบต่อวัน (`po_number` ไม่ซ้ำข้ามแผนก)

- `recomputePurchaseOrderStatusQuery` -- รับและตรวจ scope แต่ **ไม่กรองแผนกใน SQL**: `po_number` ไม่ซ้ำทั้งระบบ ผู้เรียกกรองมาก่อนแล้ว และถ้ากรอง สถานะ PO อาจไม่ถูกอัปเดตเงียบ ๆ เมื่อ shipment ถูกประทับแผนกต่างจาก PO (ทดสอบแล้วว่า PO แผนก B ที่มี shipment ประทับแผนก A ยังอัปเดตสถานะ); CASE ของสถานะไม่ถูกแตะ (`scripts/repair-po-status.mjs` พึ่งอยู่)
- `loadPrintDetails` (ชื่อผู้สร้าง / ข้อมูลติดต่อ Vendor จาก `vendors` ตามชื่อ) -- ไม่กรอง จนกว่าคำถามเรื่อง Vendor ใช้ร่วมหลายแผนกจะตัดสิน

**พฤติกรรมที่ควรรู้**

- Admin ที่ดู "ทุกแผนก" **สร้างหรือแก้ PO ไม่ได้**: ตอบ 409 `DEPARTMENT_READ_ONLY` ก่อนส่ง SQL ทุกครั้ง (ต้องเลือกแผนกก่อน)
- Vendor อ่าน/แก้ PO ของบริษัทตัวเอง **ข้ามแผนกได้** (ทั้ง GET list, GET [id], PATCH) -- ยอมรับชั่วคราวเท่านั้น **ยังไม่ได้ตัดสิน** คำถามข้อ 3 (Vendor ใช้ร่วมหลายแผนก) ยังเปิดอยู่; ส่วน Vendor POST (เสนอ PO) ใช้ scope แผนกของตัวเอง
- หัวใบสั่งซื้อยังใช้ `lab_profile` id=1 ตัวเดียว: PO ของแผนก B จะมีหัวกระดาษของแผนก A จนกว่าจะมี PR แยกที่ทำ `lab_profile` แยกแผนก (ต้องมี migration และเจ้าของอนุมัติ) -- PR-1 เพิ่มไฟล์ v36 แล้วแต่ **ยังไม่ได้รัน ยังไม่ได้เปิดใช้** พฤติกรรมนี้จึงยังเหมือนเดิมทุกอย่าง (ดูหัวข้อ 10)

**ยังเป็น legacy / ห้ามเปิด `DEPARTMENTS_ENABLED` จนกว่าจะทำ**

- `liff/orders` (POST สร้าง PO จาก LINE, PATCH ตอบรีวิว) และ `vendor/shipments` (POST) ยังส่ง `{ mode: "legacy" }` (ใน `DEPARTMENT_SCOPE_PENDING`): PO ที่สร้างจาก LINE และ shipment ที่ Vendor สร้างจึง **ไม่ถูกประทับแผนกที่ถูกต้อง** (ได้แผนกเริ่มต้น)
- **ห้ามเปิด `DEPARTMENTS_ENABLED` จนกว่ากลุ่ม 6 (สั่งซื้อผ่าน LIFF) และ `vendor/shipments` POST จะย้ายเสร็จ** (เจ้าของยืนยันแล้ว)
- เงื่อนไขสำหรับตอนย้าย `vendor/shipments` POST: ต้องประทับ shipment ด้วยแผนกของ **PO นั้น** (ไม่ใช่แผนกเริ่มต้น)
- PR-3 (`po-communication.ts` และ `purchase-order-overdue.ts` -- การแจ้งเตือน / PO เกินกำหนด) **ทำแล้ว ดูหัวข้อ 9**

## 10. v36 หัวกระดาษใบสั่งซื้อต่อแผนก (PR-1: เขียนไฟล์ migration เท่านั้น)

**สถานะ: เขียนไฟล์แล้ว แต่ยังไม่ได้รัน ยังไม่ได้ซ้อมบน Neon จริง และต้องรอเจ้าของอนุมัติก่อนเสมอ** PR-1 ไม่แก้โค้ดแอป: PO ยังไม่ถูกแยกตามหัวกระดาษของแผนก (ยังอ่าน `lab_profile` แถว `id = 1` แถวเดียว)

**ไฟล์**

- `upgrade_v36_lab_profile_per_department.sql` -- ลบ CHECK `id = 1` ของ `lab_profile` และเพิ่ม unique `lab_profile_department_id_key` บน `department_id` (1 แผนก = 1 หัวกระดาษ)
- `upgrade_v36_lab_profile_per_department_rollback.sql` -- ถอนกลับ (ลบ unique ที่ v36 เพิ่มเอง แล้วใส่ CHECK `id = 1` คืน); **ปฏิเสธและไม่แก้อะไร** ถ้ามีแถว `id <> 1` (ไม่ลบแถวให้เด็ดขาด)
- เพิ่มอย่างเดียว ไม่ INSERT/UPDATE/DELETE แถวใด แถว `id = 1` (CC) คงเดิม; รันซ้ำได้; ต้องรัน v31 และ v32 ก่อน (ถ้ายังไม่ครบจะหยุดด้วย error ก่อนแก้อะไร)
- ลำดับถอนกลับ: **v36 ก่อน** แล้ว v35 ... v32, v31 (จากมากไปน้อย)
- ชื่อ CHECK จริงบน Neon **ยังไม่ทราบ** ไฟล์จึงหา CHECK จากนิยาม (CHECK ที่คลุมคอลัมน์ `id` อย่างเดียว และเป็น `id = 1`) ไม่ใช่จากชื่อ; ถ้าเจอ CHECK อื่นบน `id` ที่ไม่ใช่ `id = 1` จะหยุดด้วย error
- ตัวรัน (`scripts/apply-migration.mjs`) **ไม่แสดง RAISE NOTICE** จึงต้องจดชื่อ constraint จริงไว้ก่อนรัน (ดูด้านล่าง) เพราะ rollback จะใส่ชื่อ `lab_profile_id_check` กลับ ซึ่งอาจต่างจากชื่อเดิม (ไม่มีผลเสีย)

**คำสั่งตรวจ (อ่านอย่างเดียว) -- รันได้ก็ต่อเมื่อเจ้าของอนุญาต และก่อนซ้อมบน Neon branch แยก**

```sql
SELECT conname, contype, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'public.lab_profile'::regclass;
SELECT id, department_id FROM lab_profile;   -- เลือกเฉพาะ 2 คอลัมน์นี้เท่านั้น
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'lab_profile';
-- trigger / view / foreign key ที่อ้างถึง lab_profile (ยังไม่ทราบสภาพจริงบน Neon)
SELECT tgname FROM pg_trigger WHERE tgrelid = 'public.lab_profile'::regclass AND NOT tgisinternal;
SELECT c.relname FROM pg_depend d JOIN pg_rewrite r ON r.oid = d.objid JOIN pg_class c ON c.oid = r.ev_class
  WHERE d.refobjid = 'public.lab_profile'::regclass AND c.oid <> 'public.lab_profile'::regclass;
SELECT conname, conrelid::regclass FROM pg_constraint WHERE confrelid = 'public.lab_profile'::regclass;
```

บันทึก **ชื่อ constraint จริง** (และผลที่เหลือ) ลงในบันทึกการ rollout ก่อนรันจริง แล้วซ้อมบน Neon branch แยกก่อน พร้อม snapshot ตามข้อ 3

**หมายเหตุสำหรับ PR-2 (ยังไม่ได้ทำ)**

- หลังลบ CHECK แล้ว `id` ยังเป็น PK ที่มี DEFAULT 1 และ `department_id` มี DEFAULT เป็น CC (จาก v31): การเพิ่มแถวของแผนกอื่นต้องระบุ `id` และ `department_id` เอง ไม่เช่นนั้นจะชน PK/unique (ล้มดัง ๆ ไม่เขียนผิดเงียบ ๆ)
- เส้นทาง legacy (ปิดสวิตช์) ยังอ่าน `id = 1` ต่อไป
- นโยบายเมื่อแผนกไม่มีแถวหัวกระดาษ (เจ้าของตัดสินแล้ว): **ปฏิเสธการสร้าง PO พร้อมข้อความที่ชัดเจน** ไม่ใช้หัวกระดาษของ CC เป็นค่าสำรอง
- หน้า Admin จัดการหัวกระดาษต่อแผนกทำใน PR-3
- PGlite (ที่ใช้ในเทสต์) พิสูจน์พฤติกรรม `lock_timeout` ภายใต้ทราฟฟิกจริงไม่ได้ เทสต์ครอบคลุมตรรกะ SQL เท่านั้น
