# แผนเปิดระบบหลายแผนก (Departments) แบบปลอดภัย

เอกสารนี้เขียนให้เจ้าของระบบอ่าน ไม่ต้องเป็นโปรแกรมเมอร์
สถานะตอนเขียน: เป็นแผนเท่านั้น ยังไม่ได้ทำอะไรกับระบบจริง (production) เลย

## 1. ทำไปเพื่ออะไร

ตอนนี้ระบบมีห้องแล็บเดียว (ห้องปฏิบัติการเคมีคลินิก รหัส `CC`)
เราต้องการให้มีงานที่สอง (งานอณูชีววิทยา) ใช้ระบบเดียวกัน แต่ข้อมูลแยกกัน ไม่ปนกัน
และคนแต่ละแผนกเห็นเฉพาะข้อมูลของแผนกตัวเอง (Admin เลือก "ดูทุกงาน" ได้ แต่ดูได้อย่างเดียว)

หลักการ: โค้ดใหม่ถูกปิดไว้ด้วยสวิตช์ `DEPARTMENTS_ENABLED` ถ้าไม่ตั้งค่า ระบบทำงานเหมือนเดิมทุกอย่าง

## 2. ลำดับการทำงาน (ห้ามข้ามขั้น)

1. นำโค้ดขึ้นระบบจริงโดย **ปิดสวิตช์** (ไม่ตั้ง `DEPARTMENTS_ENABLED`) ระบบต้องทำงานเหมือนเดิม
2. ถ่าย snapshot ของฐานข้อมูล Neon เก็บไว้ก่อน (จุดย้อนกลับ)
3. ซ้อมก่อน: สร้าง branch ใหม่จากฐานข้อมูลจริงใน Neon แล้วรันไฟล์ `upgrade_v30` ถึง `upgrade_v34` ตามลำดับบน branch ซ้อมนั้นก่อน
   ดูว่าไม่มี error และจำนวนข้อมูลเท่าเดิม
4. รันไฟล์ v30 ถึง v34 บนฐานข้อมูลจริง (ผ่าน `node scripts/apply-migration.mjs <ไฟล์> --confirm-host=<host>`)
5. **รัน v30 ซ้ำอีกครั้ง** (ทำซ้ำได้ ไม่เสียหาย) เพื่อใส่แผนกให้ผู้ใช้ที่สมัครใหม่หลังรันครั้งแรก
   ขั้นนี้ **บังคับ** ทำทันทีก่อนเปิดสวิตช์ ไม่งั้นผู้ใช้ที่ไม่มีแผนกจะเข้าระบบไม่ได้
6. แก้ route (หน้า API) ทีละกลุ่มให้กรองตามแผนก จนรายการ `DEPARTMENT_SCOPE_PENDING`
   ในไฟล์ `src/lib/department-scope-coverage.test.ts` **ว่างเปล่า** (เทสต์จะเตือนเองถ้ายังค้าง)
7. ทำให้การสร้างผู้ใช้ใหม่/การสมัครสมาชิก เขียนแผนกลงตาราง `user_departments` ด้วย
   (ผู้ใช้ที่ไม่มีแผนกจะถูกปฏิเสธการเข้าระบบ)
8. เมื่อข้อ 6 และ 7 เสร็จเท่านั้น: รัน v35 ขึ้นไป (ล็อกกฎเข้มของข้อมูล) แล้วตั้ง `DEPARTMENTS_ENABLED=true`
   แล้ว deploy ใหม่
9. จากนั้นจึงเริ่มสร้างข้อมูลในแผนกที่สอง (งานอณูชีววิทยา)

## 3. สิ่งที่อันตราย (ห้ามทำ)

- **ห้ามสร้างข้อมูลในแผนกที่สอง ก่อน PENDING ว่าง** — route ที่ยังไม่ถูกแก้จะไม่กรองแผนก
  ข้อมูลของสองแผนกจะโผล่ปนกัน และ Admin ที่ดูทุกงานอาจแก้ผิดแผนก
- **ห้ามเปิดสวิตช์ก่อนรัน v30 ซ้ำ (ข้อ 5)** — ผู้ใช้ที่ไม่มีแผนกจะถูกล็อกออกจากระบบ
  (Admin ยังเข้าได้เสมอ เพื่อมาแก้สมาชิกแผนก)
- **รหัสแผนก `LAB` ห้ามใช้เป็นรหัสแผนกเด็ดขาด** — `LAB-` เป็นคำนำหน้ารหัสวัสดุเดิมที่มีอยู่แล้ว
  ถ้าใช้ซ้ำรหัสจะชนกัน
- ห้ามรัน migration บนฐานข้อมูลจริงโดยยังไม่ซ้อมบน branch และยังไม่มี snapshot
- ห้ามลบตาราง/คอลัมน์ใหม่เพื่อ "ล้างให้สะอาด" โดยไม่ถามผู้ดูแลก่อน

## 4. ถ้าเกิดปัญหา จะย้อนกลับอย่างไร

เรียงจากเบาไปหนัก (ลองข้อบนก่อน):

1. **ปิดสวิตช์**: ลบหรือเปลี่ยน `DEPARTMENTS_ENABLED` ไม่ให้เป็น `true` แล้ว deploy ใหม่
   ระบบกลับไปทำงานแบบเดิมทันที ข้อมูลไม่หาย (นี่คือวิธีแรกที่ควรใช้เสมอ)
2. ถ้าปัญหามาจากโค้ด: ย้อน deploy ไปรุ่นก่อนหน้า (โค้ดเก่าไม่สนใจคอลัมน์ใหม่ จึงไม่พัง)
3. ถ้าต้องถอน migration: มีไฟล์ `*_rollback.sql` คู่กับแต่ละไฟล์ (เช่น `upgrade_v34_indexes_rollback.sql`)
   รันย้อนจากหมายเลขมากไปน้อย (v34 → v30) และทำเฉพาะเมื่อผู้ดูแลระบบตรวจแล้วว่าจำเป็น
4. ทางสุดท้าย: กู้จาก snapshot Neon ที่ถ่ายไว้ในขั้นที่ 2 (ข้อมูลที่เกิดหลัง snapshot จะหาย ต้องปรึกษาก่อนทำ)

## 5. ตรวจสอบว่าระบบทำงานถูกต้อง

หลังแต่ละขั้น ให้ตรวจ:

- ล็อกอินด้วยผู้ใช้ปกติ 1 คน และ Admin 1 คน ได้ตามปกติ
- จำนวนข้อมูลเดิม (วัสดุ, ประวัติ, ใบสั่งซื้อ) เท่าเดิมกับก่อนทำ
- ใน log ของระบบไม่มีข้อความ `[departments] DEPARTMENTS_ENABLED but schema not ready`
  (ถ้ามี แปลว่าเปิดสวิตช์แล้วแต่ฐานข้อมูลยังไม่พร้อม ระบบจะกลับไปใช้แบบเดิมเองและเตือนไว้)
- ใน log ไม่มีข้อความ `user rejected: no department assignment` (ถ้ามี แปลว่ามีผู้ใช้ที่ยังไม่ถูกใส่แผนก
  ให้รัน v30 ซ้ำ หรือให้ Admin เพิ่มสมาชิกแผนกให้คนนั้น)
- หลังเปิดสวิตช์: ผู้ใช้ที่มีหลายแผนกเห็นตัวสลับแผนก ผู้ใช้แผนกเดียวไม่เห็น
  และข้อมูลของแผนกที่สองไม่โผล่ในหน้าของแผนกแรก (ทดสอบด้วยข้อมูลทดลองบน branch ซ้อมก่อน)
- รันชุดทดสอบ `npx vitest run` ต้องผ่านทั้งหมดก่อน deploy ทุกครั้ง

## 6. สถานะการเบิก / รับเข้า / แจ้งเตือนของใกล้หมด

**ทำแล้ว** (มีผลเมื่อเปิดสวิตช์ `DEPARTMENTS_ENABLED` เท่านั้น):

- การเบิก การรับเข้า และการแจ้งเตือนของใกล้หมด กรองตามงานของผู้ใช้แล้ว
  ผู้ใช้จะเบิก/รับเข้าได้เฉพาะรายการของงานตัวเอง และแจ้งเตือนของใกล้หมดจะส่งถึงสมาชิกของงานนั้น
- โหมด "ดูทุกงาน" บันทึกการเบิก/รับเข้าไม่ได้ (ระบบตอบกลับว่าให้เลือกงานก่อน)
- รายการที่อยู่นอกงาน หรือรหัสที่ไม่มีอยู่จริง ได้ข้อความเดียวกันว่า "รายการนี้ไม่อยู่ในงานของคุณ"
  (จึงไม่ใบ้ว่ารหัสนั้นมีอยู่ในงานอื่นหรือไม่)
- ปิดสวิตช์ = ระบบทำงานเหมือนเดิมทุกอย่าง ไม่มี migration ใหม่ ไม่มีตัวแปร env ใหม่

**เงื่อนไขก่อนเปิดสวิตช์ (ห้ามข้าม):**

1. ต้อง merge PR `feat/departments-mobile-auth` ก่อน
   (ให้มือถือ/LIFF ที่เบิก–รับเข้า ใช้งานของ "งานหลัก" ของผู้อนุมัติ ยังไม่มีปุ่มเลือกงานบนมือถือ)
   ถ้าไม่ merge ก่อน มือถือ/LIFF จะตอบ error 500 ทุกครั้ง (ระบบปฏิเสธไว้ก่อนเพื่อความปลอดภัย แต่ใช้งานไม่ได้)
2. การเบิก การรับเข้า และการแจ้งเตือนของใกล้หมด ต้อง merge **พร้อมกันใน PR เดียว** ห้าม deploy ครึ่งทาง
   ถ้าต้องย้อนกลับ ให้ย้อนทั้งชุด
3. ก่อนสร้างข้อมูลงานที่สอง ให้ตรวจความสอดคล้องของข้อมูลสต็อกกับรายการวัสดุ ผลต้องได้ **0**:

   `SELECT count(*) FROM inventory i JOIN master_data m ON m.item_id = i.item_id WHERE i.department_id <> m.department_id;`

   ถ้าไม่ใช่ 0 แถวสต็อกที่ไม่ตรงนั้นจะ "หายจากการเบิก" แบบเงียบ ๆ (เบิกไม่ได้ ขึ้นว่าไม่พบรอบรับเข้า) ต้องแก้ข้อมูลก่อน

**ข้อควรรู้ (ผลข้างเคียงที่ตั้งใจ/ยอมรับได้):**

- Admin ที่สร้างหลังรัน v30 ครั้งสุดท้าย (หรือไม่มีแถวสมาชิกของงานนั้น) จะไม่ได้แจ้งเตือนของใกล้หมดของงานนั้น
  ทั้งที่ยังล็อกอินได้ แก้โดยให้เพิ่มสมาชิกงานให้คนนั้น
- Vendor ได้แจ้งเตือนของใกล้หมดของทุกงาน แต่เฉพาะสินค้าของบริษัทตัวเอง (ตั้งใจ)
- หน้ามือถือส่วนค้นหารายการ (`/api/mobile/lookup`) ยังคืนรายการของทุกงาน (ยังอยู่ใน `DEPARTMENT_SCOPE_PENDING`)
  ผู้ใช้มือถืออาจเลือกรายการของงานอื่น แล้วได้ข้อความปฏิเสธตอนยืนยัน ซึ่งปลอดภัยและยอมรับได้
- การแจ้งเตือน "รับเข้า/เบิก" (STOCK_RECEIVED/STOCK_DISPENSED) ไม่ได้ส่งถึงใครอยู่แล้ว ไม่เปลี่ยนแปลง
- ตัวเขียนสต็อกอื่นที่ยังไม่ได้ย้ายมากรองตามงาน ได้แก่ งานนับสต็อก (count-work-orders),
  การรับของจาก vendor shipments, การยืม-คืนน้ำยา (reagent-loans) และ inventory/reconcile
  ยังเขียนลงงาน CC ตามค่าเริ่มต้นของคอลัมน์ จึง **ห้ามใช้ในงานที่สองจนกว่าจะย้าย**
  ข้อนี้คงกฎเดิมไว้: ห้ามสร้างข้อมูลงานที่สองก่อน `DEPARTMENT_SCOPE_PENDING` ว่าง
