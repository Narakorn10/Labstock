Findings, by severity:
- **High**: `receive`, `dispense`, `logs` routes check only "logged in", not role (`src/app/api/receive/route.ts:7-10`, `dispense/route.ts:7-10`, `logs/route.ts:7-10`), so a Vendor account can change stock and read all logs via direct API calls. `GET /api/mobile/lookup` needs no login and returns items, quantities, lots and expiry dates (`src/app/api/mobile/lookup/route.ts:5`).
- **Medium**: `google-token` matches users more broadly than the sign-in callback (`src/app/api/auth/google-token/route.ts:42-50` vs `src/auth.ts:41-45`, `src/lib/auth-service.ts:77-82`); no login rate limit; legacy unsalted SHA-256 passwords never upgraded (`src/lib/auth-utils.ts:28-30`); legacy plaintext bearer tokens accepted (`auth-utils.ts:102`); Telegram webhook skips the secret check when the env var is unset (`src/app/api/telegram-webhook/route.ts:73-78`); per-request `information_schema` probing (`auth-utils.ts:49-59`, `auth-service.ts:21-35`).
- **Unconfirmed**: `notifyUsers` is not wrapped in try/catch after the stock commit (`stock-transactions.ts:138-147`), so a notification error could make a client retry and double-receive. `notifyUsers` itself was not read.
- **Good**: FOR UPDATE + `quantity >=` guard inside one transaction (`stock-transactions.ts:208-238`); password-reset flow; LINE webhook signature check.

## AI Diary (Required - 100+ words)

My first attempt at finding unauthenticated API routes was wrong. I grepped for a list of helper names I had guessed, and the real helper, `getAuthenticatedUser`, was not in my pattern, so the output listed almost every route as unprotected. I caught this only because the count of real imports did not match the route count, and I redid the scan with the actual names. Had I reported the first list, it would have been a false alarm about most of the API. I was also careful not to overstate the double-receive risk: I never opened `notifyUsers`, so I labelled it unconfirmed instead of calling it a bug. I was surprised that the project rules say there is no test framework while vitest with 78 passing tests exists, which shows the rule document has drifted from the repo. I chose not to run `npm run build` because it overwrites `.next/`, and I said so in the report. I did not open `.env.local` or the root repair scripts, and I told the user those were not reviewed.

## Lessons Learned

- **Pattern**: Never build a "routes missing X" scan from guessed names. First list the helper names that are actually imported, then scan. Cross-check the count against the number of routes.
- **Pattern**: With no `middleware.ts`/`proxy.ts`, every route must enforce its own auth and role, so "authenticated" is not the same as "authorized". Check role handling per route, especially for the external Vendor role.
- **Pattern**: Mark a suspected defect as unconfirmed when the deciding function was not read.
- **Process**: Project rule `RULES/05-lab-stock-nextjs.md:22` ("no test framework") is outdated; it was not edited.
