## AI Diary (Required - 100+ words)

I began with the assumption that the configured database could be used for a safe Preview migration, but the endpoint and Neon metadata showed that it was the production branch. Stopping there was important: the original request valued correctness over speed, and the application has real laboratory workflow and vendor-data boundaries. Creating a separate Preview branch made the rest of the investigation much clearer. The most useful surprise was that the migration could be tested beyond schema inspection: a disposable Admin account proved that a real password reset invalidated the old Auth.js session and old password. I also found a subtle authorization-quality issue in Settings: non-Admin callers were denied correctly but labeled as unauthenticated. Separating 401 and 403 improved the contract. I kept temporary credentials and tokens out of files and deleted all temporary database records, but LIFF still requires a real LINE-issued token, so it must remain an explicit release gate rather than an inferred pass.

## Lessons Learned

- **Fail-closed release gate**: A successful build and API smoke test do not replace a verified database branch, authenticated role tests, and a genuine LIFF identity.
- **Compatibility boundary**: Preserve the Auth.js and LIFF architecture in the publish checkout; do not transplant custom bearer-auth behavior from an older workspace copy.
- **Data separation**: Vendor PO responses must be explicitly shaped instead of returning broad database rows.
