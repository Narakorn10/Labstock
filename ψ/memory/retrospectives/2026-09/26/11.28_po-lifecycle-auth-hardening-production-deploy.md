## Lessons Learned

- **Pattern**: A data-modifying CTE cannot see its own siblings' writes. Anything derived from what the statement just wrote (status counters) must be a following statement in the same transaction.
- **Pattern**: Mock-`sql` unit tests do not exercise SQL semantics. Run route tests against in-memory Postgres, use the production column types, and confirm a new test fails on the old code before trusting it.
- **Pattern**: Ask for real production shape (column types, counts per vendor) before concluding a diagnosis; my first hypothesis was reasonable but wrong, and one pasted query result corrected it.
- **Pattern**: A `LIMIT` under an `ORDER BY lowest stock` silently drops the items that matter most for suggestions; explicit item lists and "evaluate everything then filter" must not share the default page size.
- **Process**: Test against a throwaway Neon branch made from production; neutralise notifications on the branch (null addresses, dummy LINE tokens), derive the branch DATABASE_URL by swapping the host without printing secrets, and delete the branch afterwards (user approval).
- **Process**: Never hand-type identifiers you only know partially (commit SHAs); read them from the tool. A guard flag that fails is working as designed.
- **Process**: Vercel here deploys production only when a PR merges into `main`; a branch push gives a Preview whose `DATABASE_URL` may be the production database.
