## AI Diary (Required - 100+ words)

I began with a detailed implementation plan but still had to challenge several assumptions in the existing v4 code. The most important distinction was that the approved laboratory quantity must remain the default PO value while the live calculation is a comparison and optional basis, not a silent replacement. I initially focused on making PO insertion transactional, then an independent review exposed a subtler race: recomputation happened before the transaction, so two requests could calculate against the same open-order state. I corrected that with ordered advisory locks and an optimistic pending-PO snapshot check inside the transaction. I also caught a temporary worker edit that removed the desktop order page during a rewrite; I stopped that path, restored the file, and applied bounded patches instead. Tests helped distinguish real defects from incorrect expectations, especially FEFO expiry timing, ETA bridge demand, and minimum-versus-multiple rounding. The final local evidence is strong, but I deliberately did not treat a successful build, unauthenticated HTTP checks, or Local RAG indexing as proof that the hospital workflow is production-ready. Database migration and authenticated acceptance still need a controlled staging environment and explicit authorization.

## Lessons Learned

- **Pattern**: Preserve policy quantity as the default while exposing the live result as a separately selectable, auditable basis.
- **Pattern**: A transaction around inserts is not enough when the decision was calculated earlier; lock and recheck the state that could make the calculation stale.
- **Pattern**: Minimum quantity and order multiple must be applied in an order that satisfies both constraints.
- **Pattern**: Migration reruns must preserve later Admin decisions instead of resetting review status or timestamps.
- **Pattern**: Build and public HTTP success do not replace authenticated desktop, LIFF, and real-Postgres workflow tests.
